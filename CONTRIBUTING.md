# Contributing

## Setup

Ruby 3.2 or newer and Bundler. Then:

```sh
bundle install
bundle exec rake               # lint, signature validation, unit tests with runtime signature checks, Rails samples
bundle exec rake test          # unit tests, the doc sample and link tests, and the examples
bundle exec rake test:rails    # the Rails guide's samples under Action Pack and Active Job
bundle exec rake test:contract # the client against a Prism mock of the spec (needs Node.js for npx)
bundle exec rake generate      # rewrite the generated code, resource reference and code samples from openapi/sdk-ir.json
bundle exec rake docs          # the YARD API reference, into doc/
gem build teachmehipaa.gemspec # the gem, into the working directory
```

## Generated and hand-written code

The library is a hand-written core plus a resource and model layer generated
from the vendored IR (ADR-0001).

| Path | Origin |
| --- | --- |
| `lib/teachmehipaa/core/`, `lib/teachmehipaa/client.rb`, `lib/teachmehipaa.rb`, `sig/teachmehipaa/core.rbs` | Hand-written |
| `lib/teachmehipaa/models/`, `lib/teachmehipaa/resources/`, `lib/teachmehipaa/{models,resources}.rb`, `sig/teachmehipaa/{models,resources}/`, `docs/reference/resources.md`, `docs/reference/code-samples.json` | Generated by `bundle exec rake generate`; do not edit |
| `lib/teachmehipaa/extensions/`, `sig/teachmehipaa/extensions/` | Hand-written methods on generated resources and models (see below) |
| `scripts/generate.rb`, `scripts/generator/` | The generator (standard library only); `scripts/generator/sample_calls.rb` holds each code sample's keywords and result line |
| `test/` | Hand-written: unit tests, the doc sample, code sample and link tests and the examples test (`test/*_test.rb`), `test/contract/`, `test/sandbox/`, `test/rails/` |
| `README.md`, `docs/guides/`, `examples/` | Hand-written, and tested (see [Documentation](#documentation)) |
| `scripts/yard_links.rb`, `.yardopts` | The YARD build of the API reference |
| `openapi/` | Vendored from the monorepo; do not edit (see `openapi/README.md`) |

Every generated file carries a "Generated from openapi/sdk-ir.json - do not
edit" banner (an HTML comment in `docs/reference/resources.md`; JSON has no
comments, so `code-samples.json` goes without). To change generated code, change the generator, or fix the IR
upstream in the monorepo's `tooling/sdk-ir` and re-vendor it.

### Hand-written methods on a resource

A resource listed in `EXTENDED_RESOURCES` (`scripts/generator/resources.rb`)
is generated as `<Name>Base`, such as `Resources::EventsBase`.
`lib/teachmehipaa/extensions/<file>.rb` subclasses it under the plain name
the client exposes (`Resources::Events`, adding `events.tail`), and
`sig/teachmehipaa/extensions/<file>.rbs` signs it. The generated
`resources.rb` requires the extension; `rake generate` refuses to run if
either file is missing. Add any new public method to the generated-surface
test's `HAND_WRITTEN_METHODS`.

### Hand-written methods on a model

A model listed in `EXTENDED_MODELS` (`scripts/generator/models.rb`) works the
same way: `Operation` is generated as `OperationBase`, and
`lib/teachmehipaa/extensions/operation.rb` subclasses it as `Operation`
(adding `wait` and `export_result`); every generated reference to the type
means the subclass. The generated `models.rb` requires the extension.

The spec leaves an Operation's `response` untyped. Methods whose Operations
settle with a known shape are listed in `OPERATION_MODELS`
(`scripts/generator/api_method.rb`) and return an `Operation` subclass that
reads it, such as `WebhookDeliveryOperation` for `webhook_subscriptions.test`
and `.redrive`.

## Regenerating from a new IR

1. Rebuild the IR in the monorepo
   (`bun tooling/sdk-ir/bin.ts --spec <spec> --out <dir>`), copy
   `openapi.developer.json`, `sdk-ir.json` and `sdk-ir.schema.json` from that
   one build into `openapi/`, and put the IR's `source.release` in
   `OPENAPI_VERSION`.
2. Run `bundle exec rake generate`. It checks the IR against its schema, then
   rewrites the generated files and their signatures, deleting ones the IR no
   longer produces. An IR shape it has no rule for stops it with an error
   rather than a guess.
3. Run `bundle exec rake`. The generated-surface test fails if the committed
   output differs from what the generator writes, or if any spec operation
   lacks exactly one public method; add new operations to its expected
   names.
4. Run `bundle exec rake test:contract`, add a call to
   `test/contract/contract_test.rb` for any new resource family, and add a
   CHANGELOG entry.

## Tests

| Command | What it runs |
| --- | --- |
| `bundle exec rake test` | Unit tests: the public client with a fake transport, webhook vectors, generated coverage, the README and guide doc test, the code samples, the doc links, the examples |
| `bundle exec rake rbs:test` | The same, with every call into the library checked against `sig/` |
| `bundle exec rake test:rails` | The Rails guide's initializer, job and webhook controller, under Action Pack and Active Job |
| `bundle exec rake test:contract` | The client against a Prism mock of `openapi/openapi.developer.json` (needs `npx`) |
| `bundle exec rake test:sandbox` | Read-only smoke test against the real Sandbox; skipped without credentials |

`rake test` runs only `test/*_test.rb`, so it never needs Node, credentials
or Rails; the contract, sandbox and Rails suites live in their own
directories. The Rails suite runs in its own process so that Active Support
can't change what the unit tests see.

Unit tests cross only the seams agreed in the spec: the public client with
`test/support/fake_transport.rb` injected as `transport:` and fake `clock:`
and `sleep:`, the pure webhook functions, and the generated surface. Take
expected values from the spec, the research docs or worked examples, never
from the code under test. No test calls the live API.

### README and guide samples

`test/readme_test.rb` keeps the README and every guide in `docs/guides/`
honest. Every `ruby` block in them must follow a `<!-- sample: <id> -->`
line (`test/support/doc_samples.rb` reads them), and every sample must
compile (`RubyVM::InstructionSequence.compile`). A README sample is named by
its id, a guide's by `<guide>/<id>` (such as `rails/webhook-controller`).
Each sample then runs here, runs in the Rails suite (the test's
`RAILS_SUITE`), or is listed in the test's `SYNTAX_ONLY` with the reason it
can't run (the Gemfile line, the routes file, and the Rails integration
test, which needs a booted app). A sample runs with every client it creates
sent to a `FakeTransport`, with the docs' environment variables set, and the
test checks what it printed (`puts` is captured) and what it sent. The
Sinatra webhook handler is driven with `Rack::MockRequest` and signed
Deliveries on the exact path they were signed for, and once on the wrong
path. A sample that uses `client` without creating it gets the Quickstart's
client. Stand-ins the prose names (`cursor_store`, `shutting_down?`) are
defined by the test. To add a sample, tag it and add a
`runs "<guide>/<id>", "<behaviour>" do ... end` check; the test fails if a
tagged sample has none. A new guide must be linked from the README's guide
list and from `docs/README.md`.

`test/rails/rails_guide_test.rb` loads the Rails guide's initializer, job
and webhook controller into one module, in boot order, with the real Action
Pack and Active Job and a small `Rails` stand-in for credentials, the
environment and the logger. It drives the controller through
`Controller.action(:create)` with signed Deliveries, and runs the job with
the test queue adapter.

`test/doc_links_test.rb` checks that every relative link in the README,
CONTRIBUTING.md, `docs/README.md`, the guides, the resource reference and
`examples/README.md` names a file that exists, and that every `#fragment`
matches a heading in its target.

### API reference code samples

`rake generate` also writes `docs/reference/code-samples.json`: one Ruby
sample per IR operationId, which the TeachMeHIPAA API reference shows when a
reader picks Ruby. The IR supplies each sample's method, accessor and
positional ids; `scripts/generator/sample_calls.rb` supplies the keywords
and the line that uses the result, with the example values every
TeachMeHIPAA library shares. The generator refuses a keyword the method
doesn't take, a missing required keyword, and an operation without an
entry. `test/code_samples_test.rb` compiles every sample and runs it through
the real client against a `FakeTransport`; each must make exactly one
request to its own operation's method and path, and print or save
something. The generated-surface test fails when the file is stale.

### Examples

`test/examples_test.rb` compiles every program in `examples/` and runs each
one against a `FakeTransport`, loading it with the credentials it reads from
the environment, and checks what it printed and sent. The webhook example's
Sinatra app is driven with `Rack::MockRequest`. A new example needs a test
there; the test fails on an example it doesn't know.

### Contract suite

`bundle exec rake test:contract` starts Prism
(`npx --yes @stoplight/prism-cli@5.16.0`) on a free port the first time a
test asks for it (`test/contract/prism.rb`), waits until it is listening,
and stops it when Minitest finishes. `test/contract/contract_test.rb` makes
one representative call per resource family. The client uses
`TokenProviders::Static` and an explicit `organization_id:`, since Prism
can't mock the form-encoded token endpoint, and the bare Prism host as
`base_url:`, since Prism serves the spec's paths without `/v1`. Prism
answers a request that breaks the spec with a 4xx, which fails the call, and
every test also fails on any request violation Prism reports in its
`sl-violations` header, which a wrapping transport collects. A harness test
checks that a deliberately invalid request is caught.

Prism serves static responses built from the spec's schemas. `--dynamic` and
`--errors` are off on purpose: Prism's own generated responses break the spec
(static strings ignore `pattern`; dynamic numbers break OpenAPI 3.1
`exclusiveMinimum`), so either flag makes valid requests fail. Response
violations are therefore ignored; the suite still checks that each response
reads into its model. Static list responses always carry a `nextCursor`, so
the suite reads one page and never auto-pages.

### Sandbox smoke test

```sh
TMH_SANDBOX_CLIENT_ID=cli_… TMH_SANDBOX_CLIENT_SECRET=tmh_cs_… bundle exec rake test:sandbox
```

It introspects the token (a Sandbox client's `mode` is `"test"`), lists
Courses and lists Learners in the Sandbox Environment. It never writes, and
CI never runs it.

## Documentation

| What | Where | Kept in sync by |
| --- | --- | --- |
| Overview, install, quickstart | `README.md` | The doc test runs its samples |
| Guides | `docs/guides/*.md`, indexed in `docs/README.md` | The doc test runs their samples (the Rails guide's in `rake test:rails`); the link test checks their links |
| Resource reference | `docs/reference/resources.md` | Generated by `rake generate`; the generated-surface test fails when it is stale |
| API reference code samples | `docs/reference/code-samples.json` | Generated by `rake generate`; `test/code_samples_test.rb` runs every sample |
| API reference | YARD, from the code's doc comments, published to GitHub Pages | `rake docs`, run by `.github/workflows/docs.yml` |
| Examples | `examples/` | `test/examples_test.rb` runs them |

`bundle exec rake docs` builds the API reference into `doc/` (git-ignored),
with the README as its front page and the guides, the resource reference and
the changelog alongside. It fails on any YARD warning (`--fail-on-warning`),
and its `docs:coverage` step fails when a public class, module, method,
attribute or constant has no doc comment. Open `doc/index.html` to read it.

- Doc comments use RDoc markup (`+code+`), which also renders the
  Markdown backticks the API descriptions carry. Avoid `{word}` outside
  `<tt>`: YARD reads it as a link.
- `@api private` hides internals from the reference: the whole `Core`
  module, and helpers such as `Config.build`. The one documented exception
  to the coverage check is the constants of generated enum modules, whose
  names and values are their documentation.
- The generator writes YARD tags into generated code: `@param` and `@return`
  on resource methods, with the same types as the RBS signatures in YARD
  notation, and `@return` on model fields. `Model.field` carries a YARD
  macro that documents each field as a reader.
- `scripts/yard_links.rb` turns the guides' relative Markdown links into
  links between the site's pages, or to the file on GitHub.

`.github/workflows/docs.yml` runs `rake docs` on every pull request and
publishes `doc/` to GitHub Pages from `main`
(`https://teachmehipaa.github.io/teachmehipaa-ruby/`). Before the first
deployment, enable Pages under Settings > Pages with **GitHub Actions** as
the source; the `github-pages` environment is created on the first run.

## Releasing

Releases go out from `.github/workflows/release.yml`, which runs only when
dispatched by hand. A run with `publish` unchecked (the default) runs lint,
signature validation, the unit and README tests with runtime signature
checks, the Rails suite, the contract suite and `gem build --strict`, lists the gem's files
and keeps the gem as the `gem` artifact. It publishes nothing. With
`publish` checked, a second job in the `rubygems` environment runs
`rubygems/release-gem`, which builds the gem from the same commit, tags it
`v<version>` and pushes it through RubyGems trusted publishing (OIDC; no
RubyGems key is stored in the repository). The gem keeps
`rubygems_mfa_required`, which trusted publishing satisfies.

Until launch, `teachmehipaa.gemspec` sets `allowed_push_host` to
`https://example.invalid`. `gem push` refuses to push to any other host, and
the publish job checks for it before tagging, so a `publish` run dispatched
by mistake fails without tagging or pushing anything. This is the Ruby
equivalent of npm's `"private": true`.

To ship (Nick):

1. On RubyGems.org, add a trusted publisher for the `teachmehipaa` gem (a
   pending trusted publisher if the gem doesn't exist yet): repository
   `TeachMeHIPAA/teachmehipaa-ruby`, workflow `release.yml`, environment
   `rubygems`.
2. In GitHub, create the `rubygems` environment under Settings >
   Environments, with yourself as a required reviewer.
3. In one PR: delete the `allowed_push_host` line from
   `teachmehipaa.gemspec`, set `VERSION` in `lib/teachmehipaa/version.rb`
   (1.0.0 for the first release), move the CHANGELOG's Unreleased entry under
   that version with the date, and update the README's pre-release note and
   installation section.
4. After it merges, dispatch **Release** on `main` once without `publish`
   and check the listed gem files, then again with `publish` checked and
   approve the `rubygems` deployment. The job tags the release commit
   `v<version>`.
5. Create a GitHub release for the tag from the CHANGELOG entry.
